# MultiBT 项目目标

> 这份文档回答一个问题：**MultiBT 到底要解决什么，以及怎样才算做成了。**
> 技术细节在 `docs/SPEC.md`；踩坑清单在 `docs/PITFALLS.md`；任务拆分在 `docs/TASKS.md`。

---

## 1. 一句话定位

> **Windows 的「多输出设备 + 自动同步」按钮。**
> 把系统声音同时送到多个输出设备，一次配置，之后**自动恢复、不用再想它**。

不做音频工作站，不做 Voicemeeter，不做驱动，不做每应用路由。

---

## 2. 要解决的原始问题

用户在真实场景里说的话：

> 「我想让客厅音箱 + 桌面音箱 + 投影同时出声，而且**我经常忘记 Voicemeeter 怎么配**。」

拆开看，这里其实是**三个**不同的问题，而现有工具只解决了第一个：

| # | 问题 | 现状 |
|---|---|---|
| 1 | 同时输出到多个设备 | SoundSync / Max-Paire / double-headphones / SoundDeck / AudioHQ 都做了 |
| 2 | 让它们**听起来同步** | 前两者只给一个手动毫秒滑杆；AudioHQ 完全没有每设备延迟 |
| 3 | 让它**一直**保持同步 + 不用重新配置 | **几乎没人做对**——漂移补偿只有 AudioHQ 做了，profile 自动恢复基本没有 |

**MultiBT 的价值在 2 和 3，不在 1。**

---

## 3. 目标（可验收）

每条都必须能用一句话判定通过与否。

| # | 目标 | 验收标准 | 为何是这个门槛 |
|---|---|---|---|
| **G1** | 一条系统音频 → N 个设备同时输出（N≥2，含蓝牙） | 3 个设备同时出声，连续 30 分钟**无爆音、无断续** | 基础能力，不达标则整个产品不成立 |
| **G2** | 每个设备独立音量 | 拖动任一滑杆，其他设备音量不受影响 | 类别标配；且必须走**链路增益**而非端点音量（否则会影响其他应用） |
| **G3** | 每个设备独立延迟补偿，多设备**听感同步** | A/B 对比**无 flam**（设备间偏差 <20 ms） | 20–40 ms 是「明显可闻」的起点；<20 ms 才是「同步」 |
| **G4** | 播放 **1 小时**期间持续保持同步 | 60 分钟后设备间偏差仍 **<5 ms** | ±50 ppm 会在 1 小时内漂移 180 ms；不补偿则 5 分钟内就失效 |
| **G5** | Profile：保存/加载场景；设备重连后**自动恢复** | 断开蓝牙音箱再连上，**无需任何操作**自动回到出声状态 | 这是「不用再想它」的全部含义 |
| **G6** | 托盘可完成全部日常操作 | 日常使用**不需要打开主窗口** | 用户不会为了听歌打开一个配置界面 |
| **G7** | 蓝牙已配对设备的连接/断开可在应用内完成 | 点 [连接] → **不打开 Windows 设置**即出声 | 差异点；且已确认无需提权、无需驱动 |
| **G8** | 延迟数字是**诚实**的 | UI 分别显示测量值/补偿值/微调值 + 离散度 + **系统总延迟** | 见下方「诚实性」 |

---

## 4. 非目标（v0.1 明确不做）

写下来是为了**避免范围蔓延**，每一条都有理由：

| 不做 | 理由 |
|---|---|
| ❌ 蓝牙**配对**新设备 | Windows 官方**不支持**桌面应用配对（`PairAsync` 标注为 desktop app unsupported）。承诺范围只能是**已配对**设备 |
| ❌ 驱动 / APO / 内核 filter | 复杂度爆炸，且会被杀软/签名问题拖死 |
| ❌ **提权**（`requireAdministrator`） | 需要提权的唯一功能（抑制 A2DP↔HFP 抖动）不值得毁掉「双击即用」的体验，且提权与 MSIX 互斥 |
| ❌ 每应用音频路由 | 那是 SoundDeck 的领域，是另一个产品 |
| ❌ EQ / 空间音频 / 音效 | 功能蔓延，偏离「同步」这个核心 |
| ❌ 网络音频（AirPlay / Snapcast） | 另一个协议栈 |
| ❌ 多房间「音乐同步」（跨房间） | 需要用户输入距离做空气传播补偿；**v0.1 只承诺同房间** |
| ❌ 单独调每个设备的频率响应 | 不是同步问题 |

## 5. 三条不可妥协的设计原则

这三条是调研后**主动收紧**的结论，也是本项目区别于「又一个多声卡复制器」的地方。

### 原则一：漂移补偿是 Tier 1，不是「第二阶段」

**量化依据：**

| 时钟误差 | 5 分钟 | 30 分钟 | 60 分钟 |
|---|---|---|---|
| 50 ppm（BT 规范 active clock 上限） | 15 ms | 90 ms | **180 ms** |
| 100 ppm | 30 ms | 180 ms | **360 ms** |

两个设备看的是**误差之差**，所以一对消费级设备一小时内可漂移 **360 ms**——
那不是「一点点偏差」，是一整句话的延迟。

**结论：不补偿漂移的应用，在 5 分钟内正确、之后永远错误。**
所以它必须进 v0.1。反过来，**声学自动测量可以推后**：它需要麦克风、需要安静环境，
而且在蓝牙上的精度下限（codec 分帧抖动 ±1–5 ms，加上校准路径与播放路径粒度差最多 ~25 ms）
**比用户自己耳听十秒钟调准还要差**。

### 原则二：诚实高于好看

**必须做的事：**

1. **测量值 / 补偿值 / 用户微调值分开显示**，绝不合并成一个「延迟」字段。
2. **测量值是相对参考设备的，不是绝对值**。麦克风自身通路的延迟是一个未知常量，
   它在**差值**中抵消、在**绝对值**中不抵消 → 所以绝对值**不可测**，
   绝不显示「你的系统延迟 240 ms」这种数字。
3. **必须显示系统总延迟**，并说明取舍：

```text
○ 音乐模式：全部对齐      → 系统延迟 ≈ 310 ms（看视频会不同步）
● 视频模式：只对齐有线组  → 系统延迟 ≈  90 ms（蓝牙单独延后）
```

因为对齐到 200–400 ms 的蓝牙设备会让**全部**输出超过 ITU-R BT.1359-1 的
~125 ms 唇音同步可察觉阈值——**「已同步」和「能看视频」在物理上互斥**。
把这个 trade-off 藏起来，就是在骗用户。

4. **测量失败就报失败**，绝不静默回退到 0 ms。
5. **测量值过期要标记**（设备重连、端点 id 变化、全局延迟变化）。
   蓝牙重配会静默重新协商 codec，SBC 与 AAC 实测差 ~60 ms，而用户看不到任何提示。

### 原则三：宁可显式失败，不要静默降级

本项目已经抓到两个**静默失效**的真实例子，都不是崩溃、都不报错，只是功能没了：

| 静默失效 | 后果 | 发现方式 |
|---|---|---|
| TFM 写成 `net10.0` 而非 `net10.0-windows10.0.19041.0` | NuGet 选到可移植组，**整个 WASAPI 栈消失**，无报错无警告 | 读到 NAudio #1407 |
| 直接读 `PKEY_Device_InstanceId` 判定蓝牙 | 该属性在 Win11 24H2 上**对所有端点都缺失** → **所有设备判定为 `Other`**，蓝牙功能静默全灭 | `tools/SmokeCheck` 实测 |

→ 因此本项目要求：**身份/分类逻辑必须有回退链，并且在目标机器上打日志核对真实值。**

## 6. 成功判据（一到两句话）

> **一次配置之后，用户不需要再打开这个应用、也不需要想起它的存在。**

具体化为可测的形式：

1. 配置 3 个设备（含 2 个蓝牙）→ 之后**只通过托盘**切换场景；
2. 关机重开 → 自动回到上次场景（G5）；
3. 蓝牙音箱断电再上电 → **不做任何操作**自动恢复（G5）；
4. 连续播放 60 分钟 → 仍听不出偏差（G4）；
5. 想看电影时，能一眼看到「会不同步」并一键切到视频模式（G8）。

---

## 7. 反目标（明确要避免的失败形态）

| 要避免 | 为什么 |
|---|---|
| 变成「又一个能同时放两个蓝牙音箱的工具」 | 那件事已经有人做了，重复造没有价值 |
| 让用户仍然需要打开 Voicemeeter / Windows 设置 | 那就没解决原始问题 |
| 把「已同步」当成永远成立的事实来展示 | 见原则二；用户一旦发现被骗就再也不信任这个应用 |
| 为了「稳定」而要求管理员权限 | 毁掉双击即用 |
| 用「反正听不出来」来为不补偿漂移辩护 | 一小时 360 ms 是听得出来的 |

## 8. 已确认可行的技术前提

这些不是计划，是**本机已经验证过**的事实（详见 `docs/SPEC.md` §1 与 `docs/PITFALLS.md`）：

| 前提 | 状态 |
|---|---|
| WASAPI loopback → N 个 WASAPI render 同时输出 | ✅ API 已验证可编译（NAudio 3.1.0） |
| 每设备独立延迟缓冲 + 运行时可调速重采样（漂移补偿的执行机构） | ✅ 已实现并通过单元测试（含闭环仿真） |
| 漂移控制律能收敛（P 控制 + 谷底目标） | ✅ 闭环仿真验证：100 ppm 下稳态偏差 0.2 ms，且不随时间累积 |
| 端点枚举能看见「已配对未连接」的蓝牙设备 | ✅ 实测：`DeviceState.All` 看到 20 个，`Active` 只看到 2 个 |
| 蓝牙设备可被正确识别 | ✅ 实测：修复身份读取后，智能音箱与 MI Portable Speaker 均判定为 `Bluetooth` |
| 蓝牙连接/断开无需提权、无需驱动 | ✅ 文档层面确认（WHQL 强制要求 `KSPROPERTY_ONESHOT_RECONNECT/DISCONNECT`）；**代码待实现（M8）** |
| 声学延迟测量算法可收敛 | ⏳ 信号生成与门限逻辑已实现并测试；**端到端待真机验证（M12）** |
